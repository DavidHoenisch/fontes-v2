# Fontes server API v1 — metadata workspace draft

Status: **implemented development scaffold including local source preparation; draft HTTP contract**, 2026-10-17. This version axis is independent of resource XML, source releases, delivery/catalog protocols, SQLite schemas and the local app command registry. It is not a native-client authentication contract or a published compatibility promise.

Implementation authority: [runtime schemas](../../../apps/fontes-site/src/lib/contracts.ts), [OpenAPI builder](../../../apps/fontes-site/src/lib/openapi.ts), [repository operations](../../../apps/fontes-site/src/lib/repository.ts) and [server migration](../../../apps/fontes-site/db/001-workspace.sql). [Running the dashboard](../../../apps/fontes-site/README.md) covers configuration, tests and limitations. The served `/api/v1/openapi` document derives input/output definitions from these schemas; don't maintain another hand-edited JSON copy.

All application operations use a verified Neon web session or the explicitly guarded local developer actor. Managed signup receives publisher capability only. Resource ownership and actor role are server-derived. Ordinary app reading is not authenticated by this API. The current native app remains separate.

Success: `{ "data": ..., "request_id": "uuid" }`. Failure: `{ "error": { "code": "...", "message": "...", "request_id": "uuid", "details": {} } }`, with optional validation details. Auth SDK routes use the provider's separate response contract. Errors include `unauthenticated` (401), `email_unverified`/`forbidden`/`origin_rejected` (403), `not_found` (404), `revision_conflict`/`invalid_transition` (409), `body_too_large` (413), `unsupported_media_type` (415) and configuration/unavailable errors (503). Unknown or malformed request fields return 400.

JSON mutations require the exact configured application Origin, same-origin fetch context when supplied, and `application/json`. Metadata bodies are limited to 16 KiB; preparation saves to 2 MiB. Raw preparation upload limits and revision headers are described below. Authentication and ownership are checked per operation. Unknown/inaccessible resources share a 404 response. Server credentials never enter response data or client code.

Resource metadata includes server-assigned identity/owner, title, description, one of the existing seven kinds, language, numeric semantic source version, independent positive concurrency revision, timestamps, owner display name and demo marker. Source version does not identify a validated archive in this scaffold. Resource IDs follow the existing namespaced syntax without replacing canonical or source-content IDs.

`GET /api/v1/workspace` returns the actor, up to 100 accessible resources, up to 30 activity events, local-runtime upload availability and organization availability and false delivery capability. `has_authoring` identifies resources with a preparation draft. Publishers see their own records; maintainers additionally see submitted/reviewed records. `GET /api/v1/resources` returns `{ items, limit: 100 }`; individual resource lookup is not restricted by that list window. Full cursor pagination remains future work.

`POST /api/v1/resources` creates an owned draft and one event atomically. `PATCH /api/v1/resources/{id}` accepts metadata plus expected `revision`, requires an owned draft or changes-requested resource, increments the revision and returns it to draft. A submitted or metadata-approved revision cannot be edited in place. Creating new source revisions after source publication needs the later immutable-source contract.

`POST /api/v1/resources/{id}/transitions` accepts `action`, expected `revision` and optional `note`:

| Action | Actor/state | Result |
| --- | --- | --- |
| `submit` | Owner of draft/changes-requested record | `submitted` |
| `request_changes` | Independent maintainer reviewing submitted record; feedback at least five characters | `changes_requested` |
| `approve_metadata` | Independent maintainer reviewing submitted record | `metadata_approved` |

An accepted transition and event commit in one database statement; competing revisions return 409 and create no second event. Creation is not idempotent; automatic retries are unsupported. If a resource has preparation data, submission additionally requires a current publisher preparation approval; an unreviewed manuscript is not silently attached to metadata review. Legacy metadata-only drafts retain their existing flow. The generic metadata PATCH rejects resources with preparation data; edit their metadata through the preparation save so approval is invalidated consistently. An editorial metadata decision cannot produce a source approval record, change trusted publishing policy, reserve a publisher claim, or authorize signing. Public disclosure is not performed by this scaffold.

## Source preparation extension

[Preparation runtime contracts](../../../apps/fontes-site/src/lib/intake-contracts.ts), [services](../../../apps/fontes-site/src/lib/intake-service.ts), and additive [authoring](../../../apps/fontes-site/db/002-authoring.sql)/[history](../../../apps/fontes-site/db/003-authoring-history.sql) migrations are authoritative. Existing metadata rows default to no preparation, without resets. Existing resource XML, source-release approval and local SQLite schemas remain unchanged.

`GET /resources/{id}/intake` returns a revisioned draft, immutable imported source inventory/hash, readable ordered blocks, proposed or supplied annotations, rights/cover fields, readiness checks, optional approval and `ai.configured=false`. The selected path is `guided` or `prepared`. IDs/prose extracted by the server cannot be injected through the save endpoint.

`PUT /resources/{id}/intake` accepts expected revision, method, metadata for guided content, rights/artwork fields and decisions by existing proposal ID. Unknown/duplicate candidate IDs are rejected. Prepared package metadata is read-only: only its attestations are edited online. An edit clears preparation approval and appends a source/proposal snapshot atomically with the version-checked update. No stale write can preserve old approval.

`POST /resources/{id}/intake/epub|prepared|cover` takes raw bytes with `X-Fontes-Revision`. It checks owner/editable state before reading bounded content. Archives: 20 MiB compressed/64 MiB expanded total, 2,000 entries and 8 MiB per expanded file. Cover: decoded upright single-frame 1200 × 1800 PNG/JPEG, at most 4 MiB. The [preparation design](../../../docs/architecture/resource-preparation.md) records narrower prose profile/text limits and the immutable prepared-package behavior. A method change after import requires a new draft. Validation failures return 422 with bounded Rust diagnostics; unsupported/unsafe archives return structured errors. Binary bytes stay in private ignored local storage, not public releases.

`POST /resources/{id}/intake/approve` accepts expected revision. Require complete fields, actual canonical coverage, explicit candidate decisions and publisher attestations. Guided output passes strict Rust validation and packing before approval is recorded. Approval includes publisher actor/time, preparation snapshot digest and exact package SHA-256. This is a publisher conversion decision, never a maintainer source/rights approval or signature. Each successful revision/approval appends a private history snapshot retaining machine provenance and human decisions.

`GET /resources/{id}/intake/cover|package` returns scoped binary assets. Source ZIP download requires owner access and unchanged snapshot/package hashes. Prepared downloads retain original bytes; guided downloads regenerate the existing XML format and deterministic Rust-packed ZIP, rejecting byte drift until renewed approval. These file operations are disabled outside local development. This is not a new installable delivery format.

Hosted upload storage/isolated validation jobs, substantive rights review, namespace verification, trusted source approvals, signing, catalog feeds, organization-private publication, offline grants, purchase fulfillment, AI enrichment/hosted study AI, full pagination/idempotency, privileged MFA and native OAuth/PKCE remain separate gates. Preserve all existing published resource/snapshot semantics when adding them. See [the server plan](../../../docs/architecture/server-components.md).

## Organization extension (D050)

The [organization runtime schemas](../../../apps/fontes-site/src/lib/organization-contracts.ts), [service](../../../apps/fontes-site/src/lib/organizations.ts), [OpenAPI definitions](../../../apps/fontes-site/src/lib/organization-openapi.ts) and additive [migration 004](../../../apps/fontes-site/db/004-organizations.sql) define the implemented management/private metadata draft contract. [Organization behavior and limits](../../../docs/architecture/organizations.md) records the role matrix, privacy and planned delivery boundary. All paths below are prefixed `/api/v1`.

| Method/path | Input and behavior |
| --- | --- |
| `GET /organizations` | Current account's complete membership list within the hard 20-membership cap |
| `POST /organizations` | Name, description, optional offline policy preference; atomic org/first owner/initial policy/event, returns 201 detail |
| `GET /organizations/{id}` | Membership-scoped detail, roster, manager-only invite history, publishing-role-only metadata drafts and latest 30 audit events |
| `PATCH /organizations/{id}` | Name/description/policy preference plus expected org revision; owner/admin, immutable policy history on actual policy change |
| `PATCH /organizations/{id}/members/{accountId}` | Desired role and expected org revision; owner/admin limits and last-owner invariant |
| `DELETE /organizations/{id}/members/{accountId}` | Expected org revision in JSON; remove within role limits |
| `POST /organizations/{id}/leave` | Expected org revision in JSON; self-leave with last-owner protection |
| `POST /organizations/{id}/invitations` | Normalized recipient email, admin/publisher/member role and org revision; 201 one-time token response, no email |
| `POST /organizations/{id}/invitations/{invitationId}` | Org revision; rotate/renew link with seven-day expiry, invalidate old token |
| `DELETE /organizations/{id}/invitations/{invitationId}` | Org revision; revoke a pending link |
| `POST /invitations/preview` | Token in JSON; matching verified email required before showing org/inviter/role/expiry |
| `POST /invitations/accept` | Token in JSON; atomically consume, create unique membership and audit; returns org detail |
| `POST /organizations/{id}/resources` | Existing metadata fields plus org revision; owner/admin/publisher, 201 updated org detail |
| `PATCH /organizations/{id}/resources/{resourceId}` | Metadata plus org revision and `resource_revision`; edit isolated private draft |

Organization revision increments for each successful settings, membership, invite or draft action. A 409 stale revision requires refreshing; do not automatically retry mutation requests. Creates are not generally idempotent. Invitation creation/renewal returns `organization_id`, `invitation_id`, `token`, `expires_in_seconds=604800` and `delivery=copy_link`. The raw token is absent from every subsequent list/detail response; store only its SHA-256 hash server-side. Use a URL fragment and remove it after reading. Never put tokens in paths/query strings, logs or audit text. Missing/wrong-email/rotated tokens return 404; expired/revoked/replayed tokens return 409. Acceptance uses token state instead of a caller-supplied org revision.

Organization role checks run under the same row lock as each write. Admins cannot change/remove owners/admins or invite/promote admins/owners; only an owner assigns ownership to existing members. Last-owner changes/leaving fail with `last_owner` (409). Capacity failures are 409; rate limits 429. Other stable codes include `invite_inactive`, `invite_exists`, `already_member` and `revision_conflict`. Member removal is effective on subsequent requests. Unknown/inaccessible organizations return 404 even for Fontes reviewers.

`offline_policy_preference` is `retain_downloads` or `renewable_lease`; `policy_revision` changes only when the preference changes. These values do not define a signed grant or lease duration. Organization detail capabilities are `manage`, `prepare_metadata`, `private_publication=false`, `email_delivery=false`, `offline_grants=false`. Org resource status is only `draft`; IDs are private metadata UUIDs, not verified source-package IDs. Personal/reviewer/intake routes never accept those private IDs. No signed feed, private compilation/publication, email or native token API is introduced.

## Local organization EPUB review (D052)

This is a separate evaluation contract, not the personal source-package API. [Runtime schemas](../../../apps/fontes-site/src/lib/epub-review-contracts.ts), [service](../../../apps/fontes-site/src/lib/organization-epub.ts) and additive [migration 005](../../../apps/fontes-site/db/005-organization-epub-review.sql) are authoritative. All endpoints require current owner/admin/publisher membership; ordinary members and unrelated platform reviewers get 404. All file operations require development runtime.

- `GET /api/v1/organizations/{id}/resources/{resourceId}/preparation`: resource/org/preparation revisions plus nullable evaluation manifest. The manifest reports source hash/bytes, bibliographic/rights claims, ordered section inventory, image inventory, statistics, normalized-text comparison and warnings; `rightsReviewRequired=true`, `exportable=false`.
- `POST` to the same path: raw EPUB, at most 20 MiB, with both `X-Fontes-Revision` and `X-Fontes-Organization-Revision`. Authorize before reading bytes and again under a row lock at commit. Retain content-addressed private local source/document/image bytes; append inventory/history and increment resource/org revisions atomically. A concurrent edit or membership change prevents the commit. Failed/orphaned local artifacts are not discoverable through the API.
- `GET .../preparation/document?document={documentId}&offset={offset}`: at most 40 blocks with safe text/marks, verified local targets, separately labeled pending detector candidates, page totals/offsets and preparation revision. Optional `block={blockId}` selects the page containing that block; it must belong to that section.
- `GET .../preparation/assets/{sha256}`: private PNG/JPEG bytes only for a digest listed in the current manifest, with integrity verification and no-store/nosniff. Arbitrary local paths or other artifacts cannot be requested.

`has_preparation` is added to organization draft metadata. Source replacement creates a new preparation revision; editing bibliographic draft metadata does not mutate source bytes or confer approval. Normalized-text mismatch returns `epub_fidelity` (422). Unsupported structure/invalid XHTML, unsafe archives, excessive work, stale revisions, integrity failures and unavailable local storage return structured errors. Bounds and honest remaining work are in the [organization guide](../../../docs/architecture/organizations.md#local-epub-evaluation-extension-d052). D052 introduces no member release, rights approval, source ZIP export, AI execution, signing or native protocol; D053 adds a separate publisher review/source export below.


## Organization publisher correction and approval (D053)

The [runtime schemas](../../../apps/fontes-site/src/lib/epub-review-contracts.ts), [service](../../../apps/fontes-site/src/lib/publisher-review.ts), generated OpenAPI and additive migrations 006–007 define the development extension. Existing extraction manifests remain immutable (`exportable=false`); the preparation reply additionally returns `reviewRevision`, nullable corrected `draft`, current `approved` and readiness `checks`. The draft contains document inventory, rights fields, cover digest, decision counts, edited block IDs, optional content approval and generated-package receipt. Original source inventory/fidelity remain separately labeled. Document pages use the corrected inventory, add `originalText`, and expose current decisions. `pending=next&after={blockId}` finds the next unresolved-reference block, wrapping through the book; none returns `no_pending_references` (404).

`PATCH .../preparation` accepts strict JSON (2 MiB): `{resourceRevision, organizationRevision, reviewRevision, command}`. Commands:

- `correct`: `documentId`, `blockId`, `segmentTexts` (same shape as the retained inline segments), and full `references` list. Each reference has `id`, `blockId`, exact `evidence`, canonical `start`, optional `end`, `method` and pending/accepted/rejected `decision`. The server determines method provenance. Text changes preserve marks/targets, redetect only that block and discard its current reference edits; edit references in a subsequent save. IDs, evidence, actual canonical ranges, text/block/section/book bounds and explicit line breaks are checked. Saves clear approval/package.
- `fields`: strict existing intake fields, including coverage, separate text/artwork rights, per-use permissions and attestations. Clears approval/package.
- `approve`: no extra fields. Requires complete readiness checks. Records actor/time and content digest bound to metadata epoch and corrected snapshot; creates no ZIP.
- `package`: no extra fields. Requires current approval; strictly validates and packs existing XML with Rust, then commits retained package SHA-256/filename/approval digest. A stale commit cannot attach bytes to changed content. Validation diagnostics are returned as 422; no automatic retry.

`POST .../preparation/cover` accepts raw upright single-frame 1200 × 1800 PNG/JPEG, max 4 MiB, with `X-Fontes-Revision`, `X-Fontes-Organization-Revision`, `X-Fontes-Review-Revision`. Decode and hash before row-locked commit; clears approval/package. `GET .../preparation/package` returns private no-store ZIP bytes only for a currently approved/generated snapshot. Hash integrity and current publishing access are rechecked. Generic metadata saves advance a metadata epoch, so edit/revert cannot revive an old approval. Reimport clears the corrected pointer and advances review revision.

All mutations recheck owner/admin/publisher membership and organization/resource/review revisions atomically with append-only pointer history and activity; 409 is a stale snapshot, not permission to overwrite. All endpoints require local development storage. Original sources, corrected prose, license fields and ZIP bytes are absent from Postgres. Accepted references are publisher `cites` assertions in the existing XML contract; original detector/human decisions remain in local snapshots. Published XSD/IDs, maintainer approval/signature protocols and native APIs are unchanged. No member publication, hosted AI or signed app package is introduced.


## Maintainer source review and unsigned publication handoff (D054)

[Runtime schemas](../../../apps/fontes-site/src/lib/source-review-contracts.ts), [service](../../../apps/fontes-site/src/lib/source-review.ts), generated OpenAPI and migrations 008–010 define a separate source review. Legacy metadata transitions cannot approve source bytes. All new endpoints currently require local development; mutation Origin and 16 KiB JSON rules apply. Current publisher ownership/team membership or platform maintainer access is rechecked, with no general access to private drafts.

- `GET /source-reviews?history=false|true`: current active accessible queue or latest 100 withdrawn/superseded records. The active global capacity is 100.
- `POST /source-reviews`: `{source,resourceRevision,consent:true,releaseNotes}`. Source is `{kind:"personal",resourceId}` or `{kind:"organization",organizationId,resourceId,organizationRevision,reviewRevision}`. Verify current approved upstream bytes and explicit public-free sharing consent; strict canonical preparation twice, frozen preview/inventory, then locked ownership/revision recheck and atomic submission/audit. Returns 201 detail. Duplicate origin revision returns `already_submitted` (409), missing publisher approval 409, missing consent 400, incompatible public permissions/validation 422, limits 413/409.
- `GET /source-reviews/{id}`: source identity/hash, status/revision, publisher approval, full metadata/rights/inventory/validation preview, current maintainer approval/handoff and latest 100 immutable audit events including decision snapshots. Inactive records retain audit details.
- `GET .../{id}/document?document={id}&offset={n}`: runtime-validated page of at most 40 source blocks plus document/block/inline assertions. Source IDs remain unchanged. Presentation is flattened; exact package and inventory files are authoritative.
- `GET .../{id}/file?path={inventoryPath}`: only a retained inventory file, scoped and hash-checked; attachment and nosniff. No arbitrary path access or uploaded markup execution.
- `GET .../{id}/package`: frozen canonical ZIP. `GET .../{id}/handoff`: retained unsigned handoff ZIP only in `handoff_ready`. Downloads recheck scope/current revision; inactive reviews reject all content routes.
- `PATCH .../{id}`: `{revision,sourceSha256,command}`. Commands `comment`, `request_changes`, `withdraw` require feedback `note` (5–4,000 characters). `approve` additionally requires `rightsReviewId`, `publisherReviewId` and all five true `checks` (`publisher`, `textRights`, `artworkRights`, `content`, `references`). `handoff` has no extra fields. Approval/changes/handoff require a platform maintainer distinct from origin creator, submitter and publisher approver; withdrawal requires current publishing authority. Missing independence is 403; stale revisions, inactive records or invalid state are 409. State/approval/handoff/revision/event commit atomically with source/membership writes.

States: `submitted → approved → handoff_ready`; changes requests set `changes_requested`, publisher updates set `superseded`, withdrawal sets `withdrawn`. Changed origins need a new approved submission, never in-place replacement of reviewed source bytes. Events preserve prior decision evidence IDs/hashes after current approval is cleared. Local handoff version reservations reject changed canonical bytes under the same resource/version; they do not assert a release exists.

The handoff contains existing strict `submission.json` and `approval.json` plus the exact reviewed source ZIP, review receipt and instructions. It contains no real policy change, signing authority or live release receipt. The separately trusted repository policy/CI must still verify actual namespace/rights approval and publish/sign through the existing pipeline. See [maintainer review](../../../docs/architecture/maintainer-review.md) for privacy, limits, synthetic verification and remaining production gates. No published source/signature/app protocol is changed.
