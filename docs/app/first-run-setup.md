# First-run library setup

Open Fontes, choose **Reading** or **Study**, and select **Continue**. Fontes checks published library releases and shows the signed download size, installed size and estimated temporary free-space requirement. Select **Download and open**. The app downloads, verifies and prepares the library, then opens Scripture automatically. The bottom action stays reachable while the screen scrolls. No account, compiler, filesystem path or storage picker is needed on desktop or Android.

Reading contains KJV and WEB. Study adds Strong’s dictionaries, Robinson Greek, Matthew Henry, Nave’s and TSK. Network access begins only after Continue; payload transfer begins only after Download and open. Cancel works while discovering, waiting for confirmation, downloading and unpacking. Failure offers Retry setup and retains the selection. A completed install reopens from app-private storage without a network request. First launch without installed content requires a connection; no offline reading seed is bundled yet. Reading Preferences offers **Download a different library** to reopen this wizard later; Back returns to the existing library, and cancellation/failure keeps it usable. This changes only whole legacy profiles, not an independently installed add-on set.

## Service and trust boundary

The toolkit-independent [`fontes-engine::bootstrap`](../../crates/fontes-engine/src/bootstrap.rs) service owns setup. Its operation identity is `library.setup`; both the GUI and `fontes-cli setup --data-dir DIRECTORY --profile reading|study` use it. This is a bootstrap lifecycle operation before an Engine exists, alongside explicit local Open. It is not a new member of the initialized engine’s 13-command registry or an advertised JSON/MCP tool. A future pre-initialization remote transport needs an explicit contract.

The background job sends bounded progress/offer/completion events and requests UI repaint through a callback. A current-thread Tokio runtime and reqwest/rustls perform cancellable HTTP requests on the setup worker. No HTTP, signature processing, decompression or SQLite validation runs in the render loop. Cancelling pending HTTP futures is polled at 100 ms; connect/read timeouts are 10/20 seconds, metadata requests are bounded to 30 seconds, and an artifact transfer to 20 minutes. SQLite integrity checks must finish before cancellation can leave their validation phase; the UI stays responsive.

The app pins `DavidHoenisch/fontes-v2`, stable content/update protocol/schema v1, registry v1, a minimum sequence of 4 and the public key in `data/trust/data-release-1.json`. It never accepts a trust root or arbitrary download URL from the release. List up to ten pages of 100 GitHub releases, require complete discovery within that bound, ignore drafts/app/source prereleases, and try up to 20 data candidates in descending numeric sequence. Verify the exact manifest bytes and raw 64-byte Ed25519 signature with the existing `FONTES-DATA-MANIFEST-V1\n` domain prefix before parsing or selecting a compatible release. Repository, tag/sequence, versions, profile membership/capabilities and size limits must match. A bad higher tag cannot authorize its contents. This chooses the highest compatible verified candidate within bounded visible discovery; a first-time client cannot prove that a server has presented the newest existing release.

Only app-constructed GitHub API/release URLs are requested. HTTPS redirects are limited to GitHub and its configured release-asset hosts, at most five hops; no account token is sent. Metadata is bounded to 64 KiB for a manifest, 64 bytes for its signature and 2 MB per listing page. Compressed/expanded library limits are 256 MiB/1 GiB. Verify actual compressed length/SHA-256 before decompression, bound emitted bytes to the signed SQLite length, limit the zstd window to 128 MiB, and verify SQLite length/SHA-256. Check SQLite integrity, foreign keys, signed build identity/counts, and the engine’s embedded canonical registry using a temporary validation user database. Only then activate content. Shared profile definitions live in `fontes-data-contracts`; the app does not depend on the data compiler, SWORD, XML publisher tooling or raw source archives.

## App-owned storage v1

All paths are selected inside the platform app-data directory. Android uses `internal_data_path`; the APK requests INTERNET but no external-storage permission. Native SQLite and zstd remain C dependencies, and TLS/platform dependencies may contain C/assembly; authored application logic remains Rust.

```text
user.sqlite                         existing notes/session database; untouched by setup
library-path.txt                    existing successful-open preference
snapshots-v1/setup.lock             one process installer at a time
snapshots-v1/high-water.json        versioned repository/channel/schema/protocol sequence record
snapshots-v1/active.json            versioned activation receipt
snapshots-v1/previous.json          previous verified receipt when available
snapshots-v1/generations/<sqlite-sha256>-<nonce>/library.sqlite
snapshots-v1/.setup-<nonce>/...      private partial download/candidate staging
```

These app-owned v1 receipts are separate from the future composed library-v2 `library/active.json` and require an explicit future migration. Exact Rust structures are authoritative: receipts have `format_version: 1`, exact manifest text, signature hex, selected profile and bounded generation name; high-water records have `format_version: 1`, pinned repository/channel/schema/protocol, sequence and exact manifest hash. Reject lower remote sequences and changed bytes at the same sequence. Record the verified high-water mark before payload transfer; cancellation does not lower it. Existing active local content remains usable when discovery fails.

A file lock serializes setup across processes. Each attempt writes fresh staging; subsequent attempts clear only abandoned `.setup-*` directories under that lock. Failed/cancelled candidates do not replace active content. Generations have unique names, so a damaged prior generation can be repaired without overwriting an open SQLite file. Flush candidate files/directories, rename the complete generation, then atomically replace the receipt using a flushed temporary file. On Unix, directory entries are also synced. The short activation section is the commit point; cancellation before it retains the old receipt. Keep previous receipts/generation files rather than deleting content potentially held by readers. Automatic generation garbage collection, previous-generation recovery UI, download resume, available-disk preflight and comprehensive platform power-loss/fault injection remain work for the full installer. Disk-write failures are recoverable; the wizard estimates additional space as compressed + expanded bytes + 32 MiB, rather than claiming measured available space.

Managed startup verifies the signed receipt and full file length/hash on the engine worker, then the engine checks schema/canonical identity before opening the actual user store. Exact bytes were integrity/FK/count checked at activation, so startup does not repeat that full scan. SHA-256 uses the existing rustls/ring crypto backend, including accelerated implementations on supported phones, instead of an unoptimized debug hashing loop. An incomplete or damaged managed library returns to setup. The service does not mutate `user.sqlite`, delete notes, combine packages or rewrite published assets. Engine commands begin only after a usable library opens. Explicit trusted-local `--library`, remembered manual imports and Reading Preferences remain advanced development paths and do not acquire signature authentication merely by opening a file.

## Verification and release limits

Ordinary tests cover signatures, repository/version/size/membership rejection, corrupt compressed/expanded data, build identity, replay/equivocation, consent before payload transfer, cancellation, process locking, active-generation/notes preservation, and discovery tags. UI checks cover chooser, confirmation/error actions and their bounds at 320×640, 390×844 and 1440×960.

The ignored `first_run_downloads_and_opens_published_library` test performs an actual public signed Reading download through the wizard, opens real Scripture, and reopens managed content without a download job. Set `FONTES_CAPTURE_DIR` and run it with `cargo test --locked -p fontes-ui-egui first_run_downloads_and_opens_published_library -- --ignored`. It needs network/GPU access and is not part of offline CI. This harness does not establish Android-device networking, lifecycle, safe areas or accessibility. Real device/window checks, background OS scheduling, a bundled offline seed, automatic updates and independent add-on installs remain distinct gates.
