# Search workspace — 2026-11-04

Implemented React/Tauri search follows the owner's refined **Search workspace** design: a dedicated mobile view, upright Scripture typography, source labels, scope tabs, matched-term emphasis and compact result rows. The search field is a pill; Close and the submit arrow are circular. Input focus highlights the outer pill without a second rectangular outline. Header/Close remain available while results scroll. Existing themes provide accents; dark sea-glass uses the approved mint/charcoal presentation.

Enter/the keyboard Search action and the arrow submit the same query. All, Scripture and Resources request their own complete engine search scope, not a filter over the current page. Pages contain up to ten results. Status shows the loaded range and whether more matches exist, not an invented total. Editing invalidates displayed/pending results; content/edition changes and dismissal invalidate pending replies. Loading, empty, error/retry and opening states are explicit. Five successful query strings are remembered in component memory only. Initial examples are labeled **Try a search**, never fabricated history.

Selecting Scripture uses `reading.select`, then opens Read and centers/cues the actual canonical destination. A resource loads complete plain text and source/author through `study.resource` inside the workspace, with existing in-place citation previews and Back to the retained results. Search itself does not navigate. Closing returns to the retained reader. Native uses the installed library; browser preview searches only its existing sample Scripture and labels that limitation. Browser sample results are not imported into native storage.

## Engine contract and compatibility

`search.query` adds optional `scope`: `all` (the default), `scripture` or `resources`. The generated command catalog remains authoritative. Omitted scope preserves existing callers; invalid values fail strict decoding. SQL applies scope before ordering/limit/offset, retaining active-edition Scripture filtering, literal AND terms, parameter binding and deterministic rank/document-ID order. Legacy egui callers explicitly retain All. No engine/toolkit dependency changes.

For All/Scripture queries containing a digit, the existing canonical parser is tried first. A valid `John 3:16`, `j3 16` or other supported reference returns its actual active-edition verse as a read-only search hit; missing text remains absent and subsequent pages are empty. Parser failures fall back to ordinary literal text search. Resources scope always searches resource text. This supersedes the old literal-only handling of reference-shaped queries; ordinary word searches retain their semantics. New UI and engine ship together; older engines may reject the new scope parameter. No published SQL, stored preferences, notes, resource bytes or permanent identities change, and no content redownload is needed.
