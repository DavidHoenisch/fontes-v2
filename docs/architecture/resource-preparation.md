# Resource preparation: offline packages and guided EPUB intake

Status: **local development implementation plus planned AI enrichment**, 2026-10-17. D049 extends [the server plan](server-components.md). The [dashboard](../../apps/fontes-site/README.md) and [server API draft](../../specs/server-api/v1/README.md) implement the initial workflow. Existing [authoring contracts](../../specs/resource-packages/v1/README.md), [authoring guide](../resource-publishing/authoring-guide.md), and Rust CLI remain authoritative for a valid Fontes source package.

## Two entry paths, one source format

**Prepared package:** an organization or individual author uses the existing offline tooling and its own content pipeline, then uploads `.fontes-source.zip`. The local server applies bounded ZIP checks and invokes the trusted Rust source validator. It reads metadata, ordered documents/blocks, artwork credits and supplied assertions into a human-readable preview while retaining the original archive bytes. Imported publisher/resource identifiers are claims pending authority review; the dashboard's internal draft identity does not silently replace them. Downloading this path returns the original uploaded ZIP, with the approval-bound byte hash checked again. Editing a prepared package means revising it offline and uploading the replacement; the wizard does not rewrite its XML or annotations.

**Guided preparation:** collect resource details, contributor/publisher, language/version, edition/date, canonical coverage, text rights and license text, explicit per-use permissions, and separate artwork rights/alt text. Upload an authorized unencrypted prose EPUB and a contract-sized cover. Build a readable preparation draft, review its conversion report and reference candidates, and explicitly approve the draft. The server generates the existing XML/index/content/rights/assets layout, strictly validates with Rust and packs a deterministic source ZIP. No alternative publisher XML dialect is introduced.

The initial guided profile supports books, commentaries, study guides and devotionals with one contributor field. Advanced translation/lexicon/word-study profiles and richer contributors are supported by the offline package path; expanding the wizard must retain their exact semantics. The current coverage form uses explicit OSIS anchors, checked against the frozen canonical registry. It is not inferred from every citation in the book. Publisher display name, namespace authority and redistribution rights are separate checks.

The two preparation paths are independent of public versus organization-private distribution and free versus paid acquisition. The preparation workspace remains personal. D050 adds [organization membership and separate private metadata drafts](organizations.md); D052 adds a separate [local full-book EPUB evaluation](../research/calvin-epub-evaluation.md) for those drafts. D053 adds local organization publisher correction/approval and validated source export below; organization distribution remains planned. The prepared source output is not a compiled `.fontes.zip`, signed release, storefront listing or app install.

## EPUB structure before inference

EPUB already supplies a package document, manifest and reading-order spine. Use that structure rather than asking a model to decide the order of the book. The [W3C EPUB specification](https://www.w3.org/TR/epub-33/#sec-spine-elem) is the external format authority. Reading-order documents are not guaranteed to be exactly one chapter each; headings remain visible blocks, and the publisher must review the resulting section boundaries.

Implemented importer behavior:

- Read the container/package documents and process XHTML files in spine order, not archive/filename/manifest order. Preserve all supported spine documents, including the words in headings, paragraphs and list items.
- Retain source archive SHA-256, original source bytes, source path, supplied element ID when present, and deterministic draft document/block IDs. Those IDs are stable for identical input and persist in saved drafts. Reimport is a new preparation revision, not a promise of anchor remapping across changed editions.
- Render only extracted text through React. Never embed uploaded HTML, execute scripts/styles or fetch remote files. Script/style content is excluded with a conversion warning; whitespace is normalized and inline presentation/navigation is flattened with a visible warning.
- Reject unsupported text/markup rather than silently dropping it: tables, inline images/SVG, MathML, embedded media, frames/objects/canvas and unwrapped reading text need offline preparation in this first importer. Reject encrypted/obfuscated, remote-resource, missing/duplicate-spine and unsupported-content EPUBs. This is a bounded UTF-8 prose importer, not a general EPUB conformance or fidelity claim.
- Reject unsafe/case-colliding paths, links, encryption and excessive actual compressed/expanded work. Prototype bounds are 20 MiB upload, 2,000 ZIP entries, 8 MiB per expanded entry, 64 MiB total actual expansion, 128 reading-order documents, 5,000 blocks and 2 million extracted characters. Saved preparation JSON is additionally capped at 3 MB. Larger/advanced books can use offline preparation, within the applicable source-validator limits.

Cover upload requires a decoded upright single-frame 1200 × 1800 PNG/JPEG at most 4 MiB. It does not crop, resize or invent artwork permissions. Source XML/XSD and image constraints remain unchanged; the local web intake's narrower limits do not redefine those contracts.

## Suggested annotations and publisher review

The current importer uses a **literal-reference detector**, not AI. It recognizes a conservative subset of full book names/OSIS abbreviations followed by explicit chapter:verse references and same-chapter ranges. It checks actual chapter/verse existence and range order against the canonical registry. It does not infer allusions, themes, quotation identity, Strong's links, missing verse text or ambiguous cross-chapter shorthand.

Each candidate is bound to a block ID, exact matched source phrase, canonical target, detector method/version and a pending/accepted/rejected decision. The source prose is unchanged. The UI places candidates beside their original paragraphs; the publisher accepts or rejects each before approval. Conservative detection is incomplete. The personal wizard needs offline authoring for missed references; the D053 organization review supports evidence-bound manual references and corrections. Never label model guesses or detector output as supplied source annotations.

Supplied prepared-package assertions remain separate and are shown as supplied annotations. They are not run through the detector or overwritten by it. The original ZIP preserves their author/source basis, concepts and exact source markup even where the readable preview simplifies presentation.

When a publisher explicitly adopts a detected literal citation, generated source XML records an author assertion under the existing supported `basis="author"` vocabulary. The preparation snapshot/history retains its detector origin, exact evidence and human decision; adoption does not erase that provenance or change the published XSD to admit `basis="machine"`. Unaccepted/rejected candidates never enter exported source XML. Future inferred/enrichment assertions need the separately reviewed provenance/enrichment contracts.

The final review shows text and section order, contributor/publisher, text/artwork rights, permissions, coverage, conversion warnings and source annotations. It requires rights authorization attestation and explicit confirmation that the rendered work/conversion report was checked against the original. No raw XML view is needed. Metadata approval, publisher preparation approval and Fontes source/rights approval are distinct operations.

## Exact revision and byte approval

The server persists preparation state with an optimistic resource revision in `fontes_cloud.resources.authoring`. Each successful edit/import and approval appends a separate snapshot in `authoring_history`, atomically with the resource update. History retains proposal method, evidence, decisions, source hash, metadata, rights and any preparation approval. Replacing an EPUB never silently retains earlier acceptance decisions.

Before accepting publisher approval, require all preparation checks, resolve every candidate, verify retained source/cover hashes, and for guided content run strict Rust validation and packing. Approval records the actor/time, snapshot digest and exact output package SHA-256. A competing edit makes approval fail with 409. Any saved edit/import clears approval; downloaded package bytes are checked against approval again. A changed packer producing different bytes requires renewed approval rather than silently changing the artifact.

If a resource has preparation data, submitting it to maintainer review requires a current publisher preparation approval. Legacy metadata-only drafts can still enter the metadata-only review flow. No publisher preparation decision can manufacture a maintainer rights approval or grant signing/default-bundle authority.

The generated/source ZIP remains editable authoring input. Public publication still needs verified publisher namespace authority, separate text/artwork rights and fidelity review, trusted exact canonical-source approval, isolated reproducible compilation, release signing, catalog publication and the app's package-native installer. Paid/private distribution adds its existing grants and transport gates. Neither path adds a title to the default library automatically.

## Planned AI enrichment service

AI assistance is explicitly labeled **not connected** in the UI and API. There is no provider/model selected, no secret configured, no simulated AI output and no model transmission in this implementation. Reader AI-context permission is not sufficient permission to send a manuscript to a third party. Publishing enrichment is also a separate product/usage decision from paid reader study tools.

The future job contract should work on the already parsed block model:

1. Obtain explicit authorized processing consent for the manuscript, chosen processor/retention scope and applicable text rights. Show cost/quota policy and a non-AI path. Keep notes, private tags, unrelated organization content and account secrets out of the request.
2. Freeze source hash, preparation revision, block identities/text hashes, tokenizer/chunking recipe, model/provider version, prompt version and registry revision. Use an isolated bounded job with durable attempts, idempotency, cancellation and cost ceilings. Treat manuscript instructions as untrusted text, not tool authority.
3. Request **structured suggestions**, not rewritten prose or model-generated XML: candidate kind (`scripture`, `allusion`, `theme`), block ID, verbatim evidence span, proposed canonical target or concept candidate, method/version, explanation and confidence. These are a future contract, not supported current API fields.
4. Validate schema, exact evidence span against immutable block text, actual canonical references and concept registry membership/namespace. Preserve unknown/ambiguous topics as unresolved proposals. Never invent registry IDs, infer verse quotation witness from wording alone, or promote a confidence threshold to automatic approval.
5. Return a readable paragraph/section review with explicit proposed-versus-supplied labels, accept/reject/correct, batch actions only after an intentional user choice, and regenerate/invalidate on text changes. Unresolved suggestions cannot enter a publishable package. The publisher's positive decision is bound to an exact revision and the final generated source bytes.
6. Keep original input, derivation/proposal provenance, human decisions, conversion warnings and generated source mapping. Distinguish approving the converted book from approving each suggestion. Fontes public review/signing remains separate even after publisher acceptance.

Production worker isolation, storage/retention and orphan cleanup, section restructuring/advanced annotation editing beyond D053, AI provider/cost/consent contracts, concept resolution and app delivery are remaining work. Do not count this local pipeline's source ZIP checks as proof of those behaviors.

## Local operating boundary and verification

JSON preparation saves are limited to 2 MiB; the existing metadata mutation limit remains 16 KiB. File uploads stream with actual byte limits, require owner access and the expected resource revision, and store private hash-addressed bytes under ignored `.local/intake`. Source payloads, covers and output ZIPs require scoped server authorization. Credentials stay out of worker environments; the local fixed CLI receives only PATH/locale/runtime variables and a temporary file/directory. Parser/pack subprocesses have a 30-second timeout and bounded output.

File import, cover serving, approval/pack and source download are disabled outside `NODE_ENV=development`. Hosted object storage and isolated background workers are not provisioned; this local filesystem/HTTP implementation is a prototype, not the production execution boundary. Database snapshots are private server state; disk retention/orphan cleanup and quota enforcement still need an operating policy.

Verification combines importer/adversarial fixtures, live HTTP/Postgres checks and the actual Rust validator/packer. Check reading order, entities/unsupported markup, replay/stale approval, owner/reviewer isolation, actual coverage, no accepted pending proposals, deterministic generated package bytes, unchanged prepared package bytes, history and edit invalidation. Review the default HeroUI wizard in the browser separately from schema/build evidence. No live AI or storefront publication is demonstrated.


## Organization publisher review (D053)

The organization review builds on the D052 full-book extraction, independently of the narrower personal wizard. Open a resource's **Read source draft**, use **Next unreviewed reference**, and choose **Edit text & references** beside a block. Original extracted text is available in the dialog. Inline segments retain existing marks, links and line breaks; text corrections keep block/document IDs and reset the block's detected references to pending. Previously saved decisions remain in immutable local snapshot history. A text save intentionally discards current manual/adopted references in that block; add/review them again against the new text. Other blocks' decisions remain intact.

Reference edits require exact evidence within the current block, unique IDs owned by that block, and a real in-order canonical OSIS range. Accept/reject/reset/remove are explicit publisher actions; a manual or corrected target records `publisher-correction-v1`. Detector provenance is retained for unchanged candidates. All accepted assertions serialize as supported `relation="cites" basis="author"`; rejected/pending assertions are omitted. Themes, allusions and AI remain unconnected. This review does not change the original fidelity claim: that claim covers the initial extraction, while corrections are a separately approved derivative.

Complete **Publication details & rights**, provide explicit text/artwork authorization and coverage (not every incidental citation), upload a conforming cover and resolve all references. **Approve reviewed draft** records the actor/time and digest of current metadata/metadata epoch, source hash, corrected document hashes, fields, cover and decisions. It does not generate bytes yet. **Generate Fontes source package** then invokes the trusted Rust validator/packer with warnings denied, retains the resulting ZIP and binds its hash to that approval. A failed build leaves the content approval and returns diagnostics; it creates no package receipt. Repeated generation with the pinned tooling is checked for reproducible bytes in the live test. Download verifies stored bytes, current digest and publishing access again. Changing content/rights/cover clears approval; changing metadata (even later reverting it) makes it stale; reimport resets the corrected review. Stale writes return 409 and do not overwrite another publisher's work.

The source export preserves ordered text, note blocks, images with source descriptions and supported emphasis. Existing XML v1 has no internal navigation link, bold/superscript or explicit line-break markup. Those semantics remain in the rich review; exported marker text remains plain text and poetry newlines remain whitespace. The UI discloses this limitation before conversion attestation. No XSD is silently extended. Missing image descriptions/unsupported source shapes can still require offline authoring; strict validation is authoritative. The output is a source ZIP, not a compiled installable package or source release.

Migrations 006–007 are additive. The current import pointer is unchanged; corrected document/field/approval/package snapshots live under private ignored `.local/org-epub` with verified SHA-256 paths. Postgres adds current snapshot/review revision, an append-only review-pointer history and a metadata epoch. Review prose/license text stay local. Role and all expected revisions are checked again while holding the same organization lock used by membership changes. Reads/downloads require owner/admin/publisher; ordinary members and unrelated Fontes reviewers have no access. Existing production guards continue to disable local processing outside development. Disk retention, cleanup, quotas, hosted isolation, real rights/namespace review, publication/signing and device grants are still open.

Verification: `npm run test:publisher-review` uses original synthetic content and actual Postgres/Rust tools for text/reference correction, exact evidence/invalid targets, manual assertions, preserved note links, stale writes, approval-before-generation, deterministic source bytes, metadata edit/revert and reimport invalidation, inaccessible accounts and immutable pointer history. Browser review verifies the default HeroUI dialogs separately. The supplied real book remains unapproved pending the owner's edition/artwork rights review.


D054 connects current publisher-approved packages to [explicit public-free maintainer source review](maintainer-review.md), with frozen canonical bytes, independent decisions/change requests and an unsigned existing-format publication handoff. An organization’s private drafts stay outside that queue until its publishing team explicitly submits a package. Trusted policy/signing/live publication remain separate from publisher preparation.
